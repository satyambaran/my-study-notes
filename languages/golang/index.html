Example: turn knowledge into an interview answer

Question: why must you keep append's return value?

Definition: a slice is a descriptor over an array. Why: append may allocate a different backing array. Example: s = append(s, x). Trade-off: preallocating capacity can reduce allocations, but aliasing must remain intentional.

Use the same four-part shape for channels, interfaces, context, and error wrapping.

01

Language foundations

Go is statically typed, compiled, garbage-collected, package-oriented, and deliberately small. Its defaults and explicit control flow are features.

Declarations

var x int gets the zero value. x := 3 is short declaration inside functions. const values are compile-time and may be untyped. iota generates successive constants.

Built-in families

Booleans; signed/unsigned integers; floats; complex numbers; byte = uint8; rune = int32; strings; arrays; slices; maps; structs; pointers; functions; interfaces; channels.

Control flow

Only for loops. if and switch may have init statements. Switch breaks automatically; use fallthrough explicitly. No truthy values.

Functions

First-class values, closures, multiple returns, variadic final parameter. All arguments are passed by value—including copied slice/map/channel descriptors.

Data, collections & memory

Most Go bugs in interviews come from aliasing, nil behavior, Unicode assumptions, or losing the result of append.

Arrays vs slices

[N]T array

Length is part of the type; values are copied on assignment/call; comparable if elements are comparable. Useful for fixed-size data and as backing storage.

[]T slice

A descriptor: pointer to backing array, length, capacity. Multiple slices may alias. append may reuse or replace the backing array—always keep its return value.

a := [4]int{1, 2, 3, 4}
s := a[1:3]          // len=2, cap=3; values [2 3]
s = append(s, 9)  // may mutate a[3] because capacity remains
copyOfS := append([]int(nil), s...) // independent copy
clear(s)              // zero elements (Go 1.21+)
Slice rules and traps
  • make([]T, len, cap) allocates backing storage; new([]T) returns a pointer to a nil slice and is almost never wanted.
  • s[:len(s):len(s)] is a full-slice expression that caps growth and forces a later append to allocate.
  • Deleting with s = append(s[:i], s[i+1:]...) preserves order; clear removed pointer slots if the backing array remains long-lived.
  • A tiny subslice can retain a huge backing array. Copy the needed portion when retention matters.
  • Nil slice and empty non-nil slice both have length 0, but may encode differently in JSON.

Unicode-safe reversal

func reverseText(s string) string {
    r := []rune(s)
    for i, j := 0, len(r)-1; i < j; i, j = i+1, j-1 {
        r[i], r[j] = r[j], r[i]
    }
    return string(r)
}

03

Structs, methods & composition

Go models behavior with methods and interfaces, and reuse with composition. There are no classes or inheritance hierarchies.

Value receiver (t T)

Receives a copy. Good for small immutable/value-like types. Its methods belong to method sets of both T and *T.

Pointer receiver (t *T)

Can mutate, avoids copying large values, and should be used consistently when any method needs it. Its method belongs only to *T's method set.

type User struct {
    ID   int64
    Name string `json:"name"`
}

func (u User) Valid() bool { return u.ID > 0 && u.Name != "" }
func (u *User) Rename(name string) { u.Name = name }

type Audit struct{ CreatedAt time.Time }
type Record struct {
    Audit              // embedded: fields/methods promoted
    Owner User          // named composition
}
Method-set nuance: the compiler may auto-take an address for an addressable value when calling v.PointerMethod(). Interface satisfaction does not get that convenience: if the required method has receiver *T, only *T implements it.
Construction, copying, equality, and options
  • Use keyed literals outside the defining package: User{ID: 1, Name: "A"}. They survive field reordering.
  • A struct is comparable only when every field is comparable. Slices, maps, and funcs are not comparable (except to nil).
  • Copying a struct copies its fields. If it contains slices, maps, pointers, mutexes, or file handles, the copy may alias or be invalid. Do not copy synchronization primitives after first use.
  • Constructors are conventions, not syntax. Return *T when identity/mutation matters; return T for small value types.
  • Functional options scale optional configuration: NewServer(WithPort(8080), WithTimeout(time.Second)). Validate conflicts at construction.
type Option func(*Server) error
func WithTimeout(d time.Duration) Option {
    return func(s *Server) error {
        if d <= 0 { return errors.New("timeout must be positive") }
        s.timeout = d; return nil
    }
}
Examples: receiver behavior, embedding, and a constructor

Value receiver does not mutate the caller

type Counter struct{ N int }

func (c Counter) BrokenIncrement() { c.N++ } // changes only the copy
func (c *Counter) Increment() { c.N++ }      // changes the caller

c := Counter{}
c.BrokenIncrement() // c.N == 0
c.Increment()       // compiler uses (&c); c.N == 1

Embedding promotes behavior but is not inheritance

type Logger struct{ Prefix string }
func (l Logger) Log(msg string) { fmt.Println(l.Prefix, msg) }

type Service struct {
    Logger              // Service gets promoted Log
    timeout time.Duration
}

func NewService(logger Logger, timeout time.Duration) (*Service, error) {
    if timeout <= 0 { return nil, errors.New("timeout must be positive") }
    return &Service{Logger: logger, timeout: timeout}, nil
}
04

Interfaces, generics & reflection

Interfaces abstract behavior at runtime; generics preserve type information at compile time. Reach for reflection last.

Interfaces

Implicit satisfaction

A type implements an interface by having its methods—no declaration. Prefer tiny consumer-owned interfaces such as io.Reader.

The typed-nil trap

An interface is nil only when both dynamic type and dynamic value are nil. An interface holding (*MyError)(nil) is non-nil.

type Store interface { Get(context.Context, string) (User, error) }

func lookup(ctx context.Context, s Store, id string) (User, error) { return s.Get(ctx, id) }

v, ok := x.(User)          // safe assertion
switch v := x.(type) {    // type switch
case User: _ = v.Name
case fmt.Stringer: _ = v.String()
}
Why can a non-nil interface contain nil?

Conceptually, an interface value is a pair (dynamic type, dynamic value). var p *Thing = nil; var x any = p gives (*Thing, nil), which differs from (nil, nil). Avoid returning typed nils as errors or interfaces; return literal nil.

Generics: reusable algorithms without losing types

type Ordered interface { ~int | ~int64 | ~float64 | ~string }

func Max[T Ordered](a, b T) T {
    if a > b { return a }
    return b
}

type Set[T comparable] map[T]struct{}
func (s Set[T]) Has(v T) bool { _, ok := s[v]; return ok }

any

Alias for interface{}. Stores any value, but operations need assertions/reflection.

comparable

Constraint for types supporting ==/!=; required for map keys.

~T

Includes defined types whose underlying type is T, e.g. type Age int.

Choose: concrete type by default; interface for substitutable behavior; type parameter when one algorithm works across related types; reflection when shape is known only at runtime (serialization/DI frameworks).
Reflection safety checklist
  • reflect.TypeOf inspects type; reflect.ValueOf inspects value.
  • A value must be settable (usually obtained from a non-nil pointer and Elem) before mutation.
  • Check Kind, IsValid, and nil-capable kinds before calling operations that can panic.
  • Reflection sacrifices compile-time safety and readability; isolate it behind a typed API.
Examples: interface satisfaction, typed nil, generic map, and reflection

Compile-time interface check and pointer method set

type Closer interface{ Close() error }
type File struct{}
func (*File) Close() error { return nil }

var _ Closer = (*File)(nil) // compile-time assertion
// var _ Closer = File{}       // does not compile

The typed-nil error bug and its fix

type MyError struct{ msg string }
func (e *MyError) Error() string { return e.msg }

func bad() error { var e *MyError; return e } // non-nil interface
func good() error { return nil }                // nil interface

Generic transform preserves concrete types

func Map[A, B any](in []A, f func(A) B) []B {
    out := make([]B, len(in))
    for i, v := range in { out[i] = f(v) }
    return out
}
names := Map([]int{1, 2}, strconv.Itoa)

Reflection: mutate only a settable value

n := 10
v := reflect.ValueOf(&n).Elem()
if v.CanSet() && v.Kind() == reflect.Int { v.SetInt(42) }

Errors, defer, panic & recover

Errors are values and part of normal control flow. Panic is for broken invariants or truly unrecoverable states—not “exceptions with different spelling.”

var ErrNotFound = errors.New("not found")

func Load(id string) (User, error) {
    u, err := repo.Get(id)
    if err != nil {
        return User{}, fmt.Errorf("load user %q: %w", id, err)
    }
    return u, nil
}

if errors.Is(err, ErrNotFound) { }       // identity through wrapping
var pathErr *fs.PathError
if errors.As(err, &pathErr) { }              // type through wrapping
ToolUseAvoid
fmt.Errorf("…: %w", err)Add operation/context while preserving cause.%v when callers need Is/As.
SentinelStable condition clients branch on: io.EOF.Exporting many sentinels that tightly couple packages.
Custom typeStructured fields or behavior, e.g. retryability.Returning a typed nil pointer as error.
errors.JoinReport multiple independent failures; Is/As traverse children.Forcing callers to parse message text.

defer precisely

  • Deferred calls execute LIFO when the surrounding function returns—normal return or panic unwind.
  • Arguments are evaluated when the defer statement executes; a closure reads captured variables later.
  • A deferred closure can inspect/change named results. Use sparingly; it can obscure flow.
  • Do not defer resource closes inside a long loop without an inner function; defers wait until the outer function ends.
f, err := os.Open(name)
if err != nil { return err }
defer func() {
    if closeErr := f.Close(); err == nil && closeErr != nil { err = closeErr }
}()
Recover boundary: recover works only when called by a deferred function in the same goroutine. Recover at process/framework boundaries to log and convert a panic; never silently continue from corrupted state.
Examples: custom errors, wrapping, joining, defer, and recovery

Structured error that supports errors.As

Collect independent cleanup failures

var errs []error
if err := cache.Close(); err != nil { errs = append(errs, err) }

HTTP panic boundary

func recoverMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if v := recover(); v != nil {
                slog.Error("panic", "value", v, "stack", string(debug.Stack()))
                http.Error(w, "internal error", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

Packages, modules & toolchain

A package is a compilation unit and API boundary. A module is a versioned collection of packages rooted at go.mod.

Visibility & layout

Uppercase identifiers are exported. Package name usually matches directory. internal/ restricts imports to its parent tree. cmd/app/main.go is a common executable layout.

Initialization

Dependencies initialize first; then package vars, then init functions; finally main. Avoid important hidden work in init.

go mod init example.com/service     # create module
go get example.com/lib@v1.2.3      # change dependency
go mod tidy                         # add needed / remove unused
go test ./codebook                 # this folder's tested examples
go test -race ./codebook           # dynamic race detection
go test -cover ./codebook          # coverage
go vet ./codebook                  # suspicious constructs
gofmt -w codebook/*.go             # canonical formatting
go build ./cmd/api                  # typical service layout, not this folder
go run ./cmd/api                    # compile + run a service
go list -deps ./...                 # inspect dependency graph

In a conventional module, use ./... for test, race, cover, and vet. This study folder also contains independent historical main examples in the same directories, so package-wide tests of the whole folder will not compile.

Module/version details interviewers probe
  • go directive sets the module's language/toolchain expectations; toolchain may suggest a toolchain.
  • go.sum records cryptographic checksums; it is not a lockfile guaranteeing one whole dependency graph.
  • Minimal version selection chooses the highest required version in the build list. Major v2+ belongs in the module path: /v2.
  • replace is useful locally or for forks, but downstream consumers do not inherit a dependency module's replace directives.
  • go work coordinates multiple local modules without temporary replace directives.
  • Build constraints go at the top: //go:build linux && amd64. Filename suffixes such as _linux.go also constrain builds.
  • //go:embed embeds files into a string, byte slice, or embed.FS at compile time.
Low-level escape hatches: unsafe, cgo, and generation
  • unsafe can bypass type and memory safety for carefully isolated interoperability/performance code. Pointer conversions obey strict lifetime/alignment rules; never smuggle pointers through uintptr across GC-visible operations.
  • cgo calls cross between Go and C, add build/deployment complexity, and obey pointer-passing rules. Batch calls and prefer pure Go unless a native library is necessary.
  • //go:generate records generation commands but go build does not run them automatically. Generated files should be reproducible and usually checked or generated in CI explicitly.
Examples: package layout, build tags, embed, and module replacement

Concurrency: goroutines & channels

Concurrency structures independently progressing work; parallelism is simultaneous execution. Goroutines are cheap, not free—every one needs an ownership and termination story.

spawn→work→signal result/error→cancel→join

Channel semantics

OperationNil channelOpen channelClosed channel
send ch <- vblocks foreverblocks until capacity/receiver permitspanics
receive <-chblocks foreverblocks until value availableimmediately yields zero value; ok=false after buffer drains
close(ch)panicssignals no more sendspanics if closed again
  • Unbuffered channel: send and receive rendezvous; provides synchronization.
  • Buffered channel: decouples up to capacity; capacity is not a substitute for backpressure design.
  • The sending side usually closes. Receivers do not close merely because they are finished.
  • Closing is not required for garbage collection; close only to communicate “no more values.”
  • Use directional API types: <-chan T receive-only and chan<- T send-only.
func worker(ctx context.Context, jobs <-chan Job, out chan<- Result) {
    for {
        select {
        case <-ctx.Done():
            return
        case job, ok := <-jobs:
            if !ok { return }
            result := process(job)
            select {
            case out <- result:
            case <-ctx.Done(): return
            }
        }
    }
}
select, fairness, timeouts, and nil channels
  • If multiple cases are ready, one is chosen pseudo-randomly; do not depend on priority.
  • default makes the select non-blocking and can create a CPU spin loop. Usually block, use a timer, or yield intentionally.
  • time.After is convenient for one-off waits; reuse a Timer in hot loops.
  • Assigning a channel to nil disables its select case—useful for state machines.
Leak test: for every send, receive, lock, and wait, ask “what unblocks this if another stage exits early?” If the answer is nothing, you have a possible goroutine leak.
Examples: channel lifecycle, select, fan-in, and semaphore

Producer owns channel closure

func numbers(n int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for i := 0; i < n; i++ { out <- i }
    }()
    return out
}
for n := range numbers(3) { fmt.Println(n) }

Timeout without leaking the worker result send

result := make(chan Result, 1) // worker may finish after caller leaves
go func() { result <- slowCall() }()
select {

Merge two streams and close after both drain

func merge[T any](a, b <-chan T) <-chan T {
    out := make(chan T); var wg sync.WaitGroup; wg.Add(2)
    forward := func(in <-chan T) { defer wg.Done(); for v := range in { out <- v } }
    go forward(a); go forward(b)
    go func() { wg.Wait(); close(out) }()
    return out
}

Synchronization & memory model

“No crash” does not mean “no race.” Synchronization provides both mutual exclusion and visibility/ordering guarantees.

sync.Mutex

Protect an invariant/shared state. Keep critical sections small; use defer Unlock when clarity wins. Never copy after use.

sync.RWMutex

Multiple readers or one writer. Not automatically faster—extra overhead and write contention can make it worse. Measure.

sync/atomic

Low-level counters/flags/pointers. Prefer typed atomics. Multi-field invariants still need a lock or immutable snapshot.

sync.WaitGroup

Wait for a known group. Add before starting, Done once, Wait at join. Pass by pointer; do not copy.

sync.Once

Run exactly once. A panic still counts as having returned; later calls do not retry.

sync.Cond / Pool

Cond waits for condition changes under a lock; always wait in a loop. Pool reuses temporary objects and may discard them anytime.

Happens-before anchors

  • A channel send is synchronized before completion of its corresponding receive; channel close is synchronized before a receive that observes closure.
  • Mutex.Unlock synchronizes before a later successful Lock on that mutex.
  • Package initialization completes before main; starting a goroutine occurs before that goroutine begins.
  • A goroutine's exit alone is not synchronization. Join it through a channel, WaitGroup, or other primitive.
Memory-model rule: in the absence of data races, Go programs behave as if goroutines were interleaved sequentially. Do not use sleeps, timing, or “word-sized reads are probably atomic” as synchronization.

Context, cancellation & patterns

context.Context carries cancellation, deadline, and request-scoped metadata across API boundaries. It is not a bag of optional parameters.

  • Take ctx as the first parameter; do not store it in a struct for ordinary requests.
  • Never pass nil; use context.Background() or TODO().
  • Always call the returned cancel function, even with a timeout, to release resources promptly.
  • Cancellation flows parent → descendants, not upward or sideways.
  • Use values only for request-scoped cross-cutting data; use a private typed key.
func Fetch(parent context.Context, url string) ([]byte, error) {
    ctx, cancel := context.WithTimeout(parent, 2*time.Second)
    defer cancel()

    req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    if err != nil { return nil, err }
    resp, err := http.DefaultClient.Do(req)
    if err != nil { return nil, err }
    defer resp.Body.Close()
    return io.ReadAll(resp.Body)
}

Minimal bounded worker pool
func Run(ctx context.Context, jobs []Job, n int) ([]Result, error) {
    in := make(chan Job)
    out := make(chan Result)
    var wg sync.WaitGroup
    wg.Add(n)
    for i := 0; i < n; i++ {
        go func() { defer wg.Done(); worker(ctx, in, out) }()
    }
    go func() { wg.Wait(); close(out) }()
    go func() {
        defer close(in)
        for _, j := range jobs {
            select { case in <- j: case <-ctx.Done(): return }
        }
    }()
    var results []Result
    for r := range out { results = append(results, r) }
    return results, ctx.Err()
}

Runtime, GC & performance

Explain the mental model, not implementation trivia. Optimize only after measurement and keep the benchmark that proves the win.

Scheduler: G–M–P

G · goroutine

Task state plus a small growable stack. Much cheaper than an OS thread, but it retains stack/references while alive.

M · machine

An OS thread executing Go code (or blocked in a syscall/cgo).

P · processor

Runtime resource required to execute Go code; roughly GOMAXPROCS Ps schedule runnable Gs onto Ms.

Work stealing balances local run queues; network polling integrates I/O readiness; preemption prevents long-running goroutines from monopolizing execution. The scheduler makes no useful ordering guarantee for your application.

Allocation & garbage collection

  • Escape analysis decides whether values can live on a stack or must outlive the frame. Inspect with go build -gcflags=-m.
  • Go's GC is concurrent and tracing. Allocation rate and live heap size drive CPU/latency cost more than “number of objects ever allocated.”
  • GOGC trades memory for collection frequency; GOMEMLIMIT gives a soft runtime memory limit. Tune only with observability.
  • Reduce needless allocations by reusing buffers judiciously, preallocating known slice/map capacity, streaming, and avoiding interface/reflection conversions in hot paths—but measure.

Production Go design

Keep domain logic boring, dependencies explicit, concurrency bounded, and boundaries defensive.

Dependency direction

Core logic depends on small interfaces it owns. Adapters implement HTTP, SQL, queues, or cloud APIs. Wire concrete dependencies in main.

API design

Accept interfaces when substitution is needed; return concrete types. Make invalid states hard to construct. Document ownership, concurrency safety, blocking, and errors.

Resilience

Timeout every remote call. Retry only transient/idempotent work, with exponential backoff and jitter. Bound queues and concurrency; shed excess load.

Observability

Structured logs + metrics + traces. Propagate context. Measure request rate, errors, latency, saturation; add domain metrics and profiles.

Request lifecycle

parse + size limit→authenticate/authorize→validate→domain→persist→map response
Production checklist
  • Configuration is validated once at startup; secrets stay outside source and logs.
  • Every external operation has context/deadline; HTTP/DB clients and pools are reused.
  • Inputs and body sizes are bounded; SQL is parameterized; templates escape output.
  • Retries have limits, jitter, classification, and idempotency; no retry storms.
  • Background goroutines have a supervisor/owner, cancellation, panic policy, and join.
  • Server handles SIGTERM: stop accepting, cancel background work, drain with deadline.
  • Errors retain internal cause in logs but expose safe stable responses to clients.
  • Health endpoints distinguish liveness from readiness; shutdown flips readiness first.
Framework and cloud note for this folder's Gin/Fiber examples

Gin and Fiber provide routing, middleware, binding, and response conveniences; they do not change the underlying engineering rules. Keep handlers thin, dependencies explicit, middleware ordered, authentication separate from authorization, and domain logic independent of the framework. Validate JWT issuer, audience, algorithm, expiry, and key rotation—not merely the signature. Fetch secrets through environment/secret-manager adapters, cache sensibly, rotate safely, and never return provider errors or credentials to clients.

Common architecture smell: declaring giant interfaces next to implementations. Define the smallest interface at the consumer; it improves cohesion, testing, and substitutability.

Rapid-fire interview Q&A

Answer before opening. Aim for 20–40 seconds each.

1. Slice vs array?

Array length is part of its value type; a slice is a descriptor over an array.

Arrays copy in full. Slices copy pointer/len/cap and may alias backing storage. Append may reallocate, so retain the returned slice.

2. Why can append change another slice?

Both slices may share a backing array.

If capacity is sufficient, append writes into that array; if not, it allocates a new one. Use copy or a full-slice expression to control aliasing.

3. Are maps safe for concurrent use?

Not for concurrent mutation, or mutation concurrent with reads.

Use a mutex/ownership goroutine; sync.Map fits specialized read-mostly or disjoint-key workloads, not as a universal replacement.

4. Value vs pointer receiver?

Choose pointer for mutation, large values, or consistency; value for small value-like types.

Method sets affect interface satisfaction: methods on *T do not make T implement the interface.

5. What is a nil interface?

Both its dynamic type and value are nil.

An interface containing a typed nil pointer is not nil. This often causes an apparently nil custom error to compare non-nil.

6. Interface vs generics?

Interface: runtime behavior substitution. Generics: compile-time algorithm reuse across a type set.

Use concrete types by default and choose the tool that expresses the actual variability.

7. When do you close a channel?

When senders must announce that no more values will arrive.

The sender/owner closes, usually exactly one owner. Do not close just to free memory, and never send afterward.

8. Buffered vs unbuffered channel?

Unbuffered is a handoff; buffered decouples sender/receiver up to capacity.

Buffering changes synchronization and backpressure, not just performance. Pick capacity from the system invariant, not guesswork.

9. Mutex or channel?

Mutex for protecting shared state/invariants; channel for transferring ownership or coordinating events.

Both synchronize. Use the simplest model, then profile contention if performance matters.

10. How do goroutine leaks happen?

A goroutine blocks forever because its completion/cancellation path disappeared.

Common causes: abandoned sends, receivers waiting on never-closed channels, missing context handling, stuck I/O, or WaitGroup imbalance.

11. What does context carry?

Cancellation, deadlines, and small request-scoped metadata.

Pass first, do not store casually, do not pass nil, call cancel, and do not use values for ordinary function options.

12. How do you handle errors idiomatically?

Return them explicitly, add operation context with %w, and inspect with errors.Is/As.

Use panic for broken invariants; keep stable error semantics separate from human-readable messages.

13. Stack vs heap in Go?

The compiler decides with escape analysis.

Returning a local pointer is safe. Prefer clear code, then use compiler diagnostics/profiles if allocation cost matters.

14. How does Go schedule goroutines?

Goroutines (G) run on OS threads (M) using runtime processors (P).

Local queues, work stealing, network polling, and preemption coordinate execution. Never rely on scheduling order.

15. How would you debug a slow Go service?

Start from symptom and workload, then measure the dominant resource.

Metrics/traces locate the area; CPU/heap/block/mutex profiles or runtime trace explain it. Optimize, benchmark, and validate production effects.

16. How do you design a graceful shutdown?

Stop new work, cancel background work, drain in-flight work with a deadline, then release dependencies.

On SIGTERM mark unready, call server shutdown with timeout, wait for workers, flush telemetry, and exit nonzero on failed shutdown if appropriate.

17. What is the Go memory model answer in one line?

A read is reliably ordered after a write only through a defined synchronization event.

Race-free programs get sequentially consistent behavior; use channels, locks, atomics, and joins—not timing assumptions.

18. What makes Go code idiomatic?

Small APIs, explicit errors, useful zero values, composition, consumer-owned interfaces, and straightforward control flow.

Plus gofmt, standard tools, context-aware boundaries, bounded concurrency, and comments that explain why.

Examples: answer three common design scenarios aloud

“Process 10,000 URLs without exhausting resources”

I would use a fixed worker pool or errgroup with a concurrency limit, reuse one HTTP client, put a timeout on each request, propagate cancellation, collect results through an owned channel, close it after workers join, and define retry/backpressure policy.

“A service's memory keeps growing”

I would distinguish heap growth from RSS, inspect heap in-use and allocation profiles, check goroutine counts/leak profiles, look for retained slice backing arrays, caches without bounds, unread response bodies, and stuck goroutines, then reproduce with a benchmark or load test.

“Where should an interface live?”

Usually next to the consumer, describing only what that consumer needs. The concrete producer returns its own type. This avoids speculative abstractions and lets tests provide tiny fakes.

The final 10-minute sheet

Read this immediately before the interview.

Language

  • Everything passed by value.
  • Slice = ptr/len/cap; append may reallocate.
  • Map order unspecified; map mutation needs sync.
  • String bytes; range yields decoded runes + byte indexes.
  • Pointer receiver method set belongs to *T.

Interfaces & errors

  • Implicit implementation; consumer owns small interface.
  • Typed nil inside interface is non-nil.
  • Wrap with %w; inspect with Is/As.
  • Defer is LIFO; args evaluated immediately.
  • Panic only for broken invariants/boundaries.

Concurrency

  • Every goroutine: owner, stop path, join path.
  • Sender owns close; closed receive returns zero/false.
  • Nil channel blocks; nil select case is disabled.
  • Lock state; channels coordinate/transfer ownership.
  • Context first; cancel always; run -race.

Production

  • Bound time, input, concurrency, queues, retries.
  • Reuse HTTP clients and DB pools; close bodies/rows.
  • Parameterize SQL; use tx consistently.
  • Test properties and edges; profile before tuning.
  • Graceful shutdown: stop → drain → release.

Example: a complete final coding skeleton
func ProcessAll(ctx context.Context, inputs []Input, limit int) ([]Output, error) {
    g, ctx := errgroup.WithContext(ctx)
    g.SetLimit(limit)
    outputs := make([]Output, len(inputs))

    for i, in := range inputs {
        i, in := i, in // harmless on modern Go; needed for old loop semantics
        g.Go(func() error {
            out, err := ProcessOne(ctx, in)
            if err != nil { return fmt.Errorf("input %d: %w", i, err) }
            outputs[i] = out // distinct element per goroutine
            return nil
        })
    }
    if err := g.Wait(); err != nil { return nil, err }
    return outputs, nil
}

This demonstrates bounded concurrency, cancellation, deterministic output positions, error context, joining, and safe independent writes.
